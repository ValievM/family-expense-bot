# ТЗ на дизайн веб-панели «Семейные расходы»

Документ для дизайнера. Здесь описано **что интерфейс должен уметь и поддерживать**, а не как он должен выглядеть. Визуальное направление, стиль, палитру, типографику и композицию предлагаешь ты: нужно **три разных варианта** на выбор (см. раздел 12).

Цель владельца проекта: интерфейс, который выглядит дорого и продуманно, при этом остаётся быстрым, доступным и работающим на текущем бэкенде без изменений.

---

## 1. Что за продукт

Сервис учёта семейных расходов. Члены семьи пишут боту в Telegram («кофе 350»), траты сохраняются автоматически. **Веб-панель нужна главе семьи**: видеть траты всех, искать, править ошибки бота, добавлять и удалять траты вручную.

- Пользователь панели один: глава семьи. Это не публичный сервис и не соцсеть, это рабочий инструмент, которым пользуются регулярно, чаще после того, как бот что-то записал неправильно.
- **Авторизации нет** (по условию задания). Панель открывается сразу. Не рисуй экран входа, регистрации, профиля, выхода.
- Язык интерфейса: **русский**. Все тексты в макетах на русском. Деньги в рублях.
- Панель открывается на компьютере (основной сценарий) и на телефоне (быстро проверить, поправить).

## 2. Главные сценарии (в порядке важности)

1. **Посмотреть, что потратили** за период: сколько всего, на что, кто.
2. **Найти конкретную трату** (по человеку, категории, датам) и **исправить** её (сумма, категория, дата, комментарий).
3. **Удалить** ошибочную трату.
4. **Добавить** трату вручную члену семьи (например, наличные, о которых бот не знает).
5. **Быстро понять картину**: итог, топ категорий, динамика (раздел 7, необязательно).

Дизайн должен делать первые четыре сценария максимально быстрыми: по возможности без перехода на другие страницы, с минимумом кликов.

## 3. Данные, с которыми работает интерфейс

### 3.1. Трата (Expense)

| Поле | Тип и формат | Как показывать |
|---|---|---|
| `id` | число | технический, показывать можно мелко или в деталях |
| `user_id` | Telegram ID, целое положительное (до ~10 цифр, например `1234567890`) | **имён у людей нет, только ID** (см. 3.3) |
| `amount` | целое число копеек в API; в интерфейсе рубли с копейками: `350,00 ₽`, `1 299,90 ₽` | разделитель тысяч неразрывным пробелом, запятая как десятичный знак; значения от `0,01 ₽` до `1 000 000 000 ₽` |
| `category` | один из 7 ключей (3.2) и русская подпись `category_label` | цветом и/или иконкой плюс текст (не только цвет) |
| `spent_at` | календарный день `ГГГГ-ММ-ДД`, без времени | формат `16.10.2026`; для недавних дат допустимо «сегодня», «вчера» |
| `comment` | текст до 500 символов, может быть пустым | в списке одной строкой с обрезкой; полностью в деталях и в форме |
| `created_at`, `updated_at` | дата и время | второстепенно: «изменено …», например в деталях |

### 3.2. Категории (закрытый список, порядок фиксирован)

| Ключ | Подпись |
|---|---|
| `food` | еда |
| `transport` | транспорт |
| `housing` | жильё |
| `entertainment` | развлечения |
| `health` | здоровье |
| `shopping` | покупки |
| `other` | другое |

Список приходит из `GET /api/categories`. Подписи и порядок не хардкодятся. Новая категория может появиться, поэтому цвет и иконка должны задаваться таблицей соответствия с **запасным оформлением** для неизвестной категории.

### 3.3. Члены семьи

Существует только `user_id`. Список приходит из `GET /api/users` (все, у кого есть хотя бы одна трата). **Имён, аватаров и ролей в бэкенде нет.**

Дизайнеру нужно решить, как показывать человека, у которого есть только число. Предложи хотя бы одно решение, например: аватар-«монограмма» с детерминированным цветом по ID, сокращённый ID (`…7890`), возможность дать человеку **локальное имя** (хранится только в браузере, localStorage), с чёткой пометкой, что имя видно только на этом устройстве. Если для решения нужна доработка бэкенда (хранить имена), пометь это как отдельное предложение и дай **вариант без него**.

### 3.4. Объёмы

Для семьи: десятки трат в месяц, сотни и тысячи за год. Список сейчас загружается целиком (пагинации в API нет). Учитывай, что в списке может быть и 3 строки, и 2 000. Для больших списков предложи приём (группировка по дням/месяцам, «показать ещё», виртуализация), но он должен работать на текущем API.

## 4. Экраны и области

Ниже функциональный состав. Раскладку (одна страница, вкладки, боковая панель, и так далее) выбираешь ты.

### 4.1. Главный экран: список трат

Обязательно:

- **Шапка/контекст**: название продукта, текущий период в понятном виде, кнопка «Добавить трату» (всегда доступна, на телефоне допустима плавающая кнопка).
- **Панель фильтров** (раздел 5).
- **Итог по текущей выборке**: сумма всех показанных трат, количество; обновляется при смене фильтров.
- **Список трат**, новые сверху (по дню, затем по `id` убыванию). Для каждой траты: дата, человек, категория, комментарий, сумма. Строка кликабельна (детали/правка), действия «изменить» и «удалить» достижимы с клавиатуры и мыши.
- **Выравнивание сумм по разряду** (моноширинные цифры или tabular-nums), отрицательных сумм нет.
- Состояния: загрузка, пусто, пусто из-за фильтров, ошибка (раздел 8).
- **Группировка по дням** (необязательно, но приветствуется): заголовок дня с суммой за день.

### 4.2. Создание и правка траты

Один компонент формы на оба сценария (диалог, панель сбоку или отдельная страница, решает дизайнер). Поля:

| Поле | Поведение |
|---|---|
| Член семьи | **выбор из известных** + способ **ввести новый Telegram ID** (когда человек ещё не писал боту). При правке поле **только для чтения** (владельца менять нельзя) |
| Сумма, ₽ | текстовое поле, принимает `350`, `350,5`, `350.50`; не принимает отрицательные, ноль, более двух знаков после запятой, буквы; подсказка формата; на телефоне цифровая клавиатура |
| Категория | выбор из 7 (удобно: крупные «чипы»/плитки с иконкой, а не длинный выпадающий список) |
| Дата | по умолчанию сегодня; быстрые варианты «сегодня», «вчера»; нативный или собственный календарь; будущие даты разрешены |
| Комментарий | необязательный, счётчик символов при приближении к 500 |

Требования:

- **Ошибки у полей**, понятные и на русском, показываются по месту, не одним общим баннером; ошибки сервера (раздел 8.2) тоже привязываются к нужному полю, когда это возможно.
- Кнопка сохранения блокируется на время запроса, показывает прогресс; повторная отправка невозможна.
- Закрытие с несохранёнными изменениями: подтверждение или явное сохранение черновика.
- **Правка отправляет только изменённые поля**. Если ничего не изменилось, «Сохранить» неактивна.
- Работа целиком с клавиатуры: Enter отправляет, Esc закрывает, фокус возвращается на вызвавший элемент.
- После успеха: список обновляется, изменённая запись **подсвечивается** на короткое время, без перезагрузки страницы.

### 4.3. Удаление

- Удаление необратимо (на сервере нет корзины). Нужно **явное подтверждение** с показом, что именно удаляется (сумма, дата, категория, комментарий).
- Допустимо дать «Отмену» через отложенное выполнение (например, 6-8 секунд) как отдельную идею, только если это не обманывает пользователя: предупреди, что запись удаляется по истечении времени.

### 4.4. Детали траты (необязательно)

Если решишь делать: полный комментарий, человек, категория, дата, `создано` и `изменено`, кнопки «изменить» и «удалить».

### 4.5. Пустое состояние «первого запуска»

Когда трат нет вообще: объясни, как они появляются («напишите боту в Telegram: “кофе 350”»), покажи пример сообщения и кнопку «Добавить трату вручную». Это важный момент первого впечатления.

## 5. Фильтры

Все фильтры можно комбинировать; состояние **хранится в адресной строке** (ссылку на выборку можно скопировать и открыть заново; это уже работает).

| Фильтр | Значения | Заметки |
|---|---|---|
| Член семьи | «Все» или один из списка | параметр API `user_id` |
| Категория | «Все» или одна из 7 | параметр `category` |
| Период | произвольные «с» и «по» (оба необязательны, включительно) | параметры `from`, `to`, формат `ГГГГ-ММ-ДД`; «с» не позже «по» |

Требования:

- **Быстрые пресеты периода**: сегодня, вчера, эта неделя, этот месяц, прошлый месяц, последние 30 дней, год, свой диапазон. Пресеты сводятся к `from`/`to` (на бэкенд их передавать не нужно).
- Видно, **какие фильтры включены** (чипы/подсказка), и есть «Сбросить всё» и сброс по одному.
- Проверка периода: если «с» позже «по», понятная подсказка (сервер вернёт `invalid_period`).
- Изменение фильтра обновляет список без перезагрузки страницы и без «мигания» (старые данные остаются на экране, пока приходят новые, с ненавязчивым индикатором).
- Поиск по тексту комментария в API **нет**. Если нужен, он может быть только клиентским по уже загруженному списку: пометь это ограничение.

## 6. Что API может и не может (чтобы не рисовать невозможное)

База: `/api`, JSON. Подробный контракт: `docs/openapi.yaml`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/expenses?user_id=&category=&from=&to=` | список, новые сверху, **без пагинации** |
| `POST /api/expenses` | создать (`user_id`, `amount` в копейках, `category`, `spent_at`?, `comment`?) |
| `PATCH /api/expenses/{id}` | частичное изменение (`amount`, `category`, `spent_at`, `comment`) |
| `DELETE /api/expenses/{id}` | удалить (204) |
| `GET /api/users` | члены семьи (только ID) |
| `GET /api/categories` | категории |

**Нельзя без доработки бэкенда**: поиск по тексту, сортировка по другому полю, серверная пагинация, агрегаты («сумма по категориям»), имена людей, вложения и чеки, бюджеты и лимиты, теги, экспорт, несколько валют (только рубли), уведомления в реальном времени, смена владельца у существующей траты.

Всё из раздела 7 («аналитика») считается **на клиенте** по загруженной выборке.

## 7. Необязательные возможности (если улучшают впечатление и не усложняют основное)

Предлагай как отдельный слой, помечая «основа» и «дополнение»:

- **Сводка по выборке**: сумма, число трат, средний чек, самый затратный день.
- **Разбивка по категориям**: доли в виде полосы или диаграммы с подписями и значениями (доступно без цвета: подписи и проценты).
- **Разбивка по людям** (кто сколько потратил).
- **Динамика по дням или неделям** (небольшой график), с доступной альтернативой в виде таблицы.
- Сравнение с предыдущим периодом такой же длины (клиентский расчёт вторым запросом по `from`/`to`).
- Экспорт выбранного в CSV на стороне клиента.
- Быстрое действие «повторить трату» (создать копию с сегодняшней датой).
- Горячие клавиши (`N` новая трата, `/` фокус на фильтры, `Esc`) и их подсказка.

Каждое такое решение должно **работать при пустых, малых и очень больших данных**.

## 8. Состояния и ошибки (проработать все)

### 8.1. Состояния экрана

| Состояние | Что показать |
|---|---|
| Первая загрузка | скелетоны под реальные формы строк, не «крутилка» на весь экран |
| Повторная загрузка (смена фильтра) | прежние данные остаются, тонкий индикатор |
| Данных нет вообще | пустое состояние первого запуска (4.5) |
| Нет результатов по фильтрам | «Ничего не найдено» + кнопка сброса фильтров, без путаницы с «данных нет» |
| Сервер недоступен | понятная ошибка и «Повторить»; данные, если уже были, остаются на экране |
| Сохранение / удаление в процессе | блокировка действия, индикатор на нужном элементе |
| Успех | краткое ненавязчивое подтверждение (тост или подсветка), не блокирующее работу |

### 8.2. Ошибки сервера

Формат: `{"error": {"code": "...", "message": "..."}}`. Коды и как их показывать:

| Код | Когда | Показ |
|---|---|---|
| `invalid_amount` | сумма нулевая, отрицательная, слишком большая или с лишними знаками | у поля «Сумма» |
| `invalid_user` | неверный Telegram ID | у поля «Член семьи» |
| `unknown_category` | категория не из списка | у поля «Категория» |
| `invalid_date` | неверная дата | у поля «Дата» |
| `comment_too_long` | более 500 символов | у поля «Комментарий» |
| `invalid_period` | «с» позже «по» | у фильтра периода |
| `invalid_json`, `invalid_id` | ошибка клиента | общий баннер, технические детали свернуты |
| `not_found` | запись уже удалена (например, ботом или другим окном) | «Запись не найдена, список обновлён» и автообновление |
| `internal` | сбой сервера | общий баннер «Что-то пошло не так», «Повторить» |

Тексты ошибок пишет дизайнер/копирайтер: короткие, на «вы», без технических терминов и без вины пользователя.

## 9. Поведение и взаимодействие

- **Без перезагрузок страницы**: все изменения и фильтры обновляют данные на месте.
- **Оптимистичные обновления допустимы** только с откатом при ошибке; иначе после успешной операции просто перезапросить список.
- **Адресная строка** отражает фильтры (кнопки «назад/вперёд» браузера работают осмысленно).
- **Запоминание** удобных мелочей на устройстве (последний выбранный человек в форме, тема): только в localStorage, и интерфейс обязан работать, если он недоступен.
- **Одновременные изменения**: бот может добавить трату, пока панель открыта. Предложи ненавязчивый способ обновить данные («Есть новые траты, обновить»), без автообновления, которое сбивает прокрутку и фокус. Реального времени (push) нет: допустим опрос раз в минуту или обновление по возвращению на вкладку.
- **Анимации**: полезные (появление, подсветка изменённой строки, переходы диалогов), короткие (до ~250 мс), уважают `prefers-reduced-motion`.

## 10. Адаптивность

| Ширина | Требование |
|---|---|
| 360-480 px (телефон) | всё доступно одной рукой; список превращается в карточки; фильтры сворачиваются в «Фильтры (N)»; форма на весь экран или нижняя панель; кнопки не менее 44×44 px |
| 768-1024 px (планшет) | промежуточная раскладка, без горизонтального скролла |
| 1280 px и шире | основной сценарий: плотный список/таблица, боковые элементы, обзор |
| 1920 px и шире | контент не растягивается бесконечно: ограничение ширины или осмысленное использование места |

Горизонтальной прокрутки страницы быть не должно ни на одной ширине. Учитывай безопасные зоны на телефонах (вырезы, домашний индикатор) и портретную/альбомную ориентации.

## 11. Требования к качеству

### 11.1. Доступность (уровень WCAG 2.2 AA)

- Контраст текста не ниже 4.5:1 (крупного 3:1), контраст значимых элементов интерфейса не ниже 3:1, **в обеих темах**.
- Информация не передаётся одним цветом (категории: цвет плюс подпись/иконка).
- Полная работа с клавиатуры, видимый и красивый фокус, логичный порядок табуляции, диалоги ловят фокус и возвращают его.
- Семантика: правильные заголовки, поля с подписями, таблица или список с понятной структурой для скринридеров; ошибки и успех озвучиваются (`aria-live`).
- Цели нажатия не меньше 24×24 px (по WCAG), на телефоне не меньше 44×44 px.
- Масштабирование текста до 200% не ломает раскладку.
- `prefers-reduced-motion`, `prefers-color-scheme`.

### 11.2. Темы

**Светлая и тёмная обязательны**, переключаются по системным настройкам и вручную (с запоминанием выбора). Обе должны быть проработаны полностью, а не инверсией.

### 11.3. Производительность

- Ничего тяжёлого: целевой размер JS после сборки не более ~250 КБ gzip (сейчас около 50 КБ), без больших библиотек ради одного эффекта.
- Шрифты: поддержка кириллицы обязательна; подключаются через Google Fonts или системные; не более 2 начертаний/семейств, `font-display: swap`. Цифры в суммах должны быть табличными (`tabular-nums`).
- Иконки: SVG (встроенные или небольшой набор), без шрифтов-иконок.
- Изображения и иллюстрации: только лёгкие SVG; никаких внешних картинок с чужих доменов.
- Список из 2 000 строк не должен «тормозить» ввод.

### 11.4. Тексты и тон

Спокойный, дружелюбный, деловой, без восклицаний, жаргона и «шуток про деньги». Обращение на «вы». Единый словарь: «трата», «член семьи», «категория», «период». Деньги всегда с символом `₽`.

## 12. Что нужно от дизайнера (результат работы)

1. **Три разных направления** (концепции) с краткой идеей каждого: настроение, плотность, характер, ключевые решения. Они должны отличаться по сути (плотная «рабочая таблица», воздушный «финансовый дашборд», «карточный» мобильный первый подход и подобное), а не только цветом.
2. Для каждого направления макеты **главного экрана** и **формы создания/правки** минимум в двух ширинах (телефон 390 и компьютер 1440), в светлой и тёмной теме.
3. После выбора владельцем одного направления: **полный комплект**:
   - все экраны и состояния из раздела 8 (загрузка, пусто, нет результатов, ошибки, успех, подтверждение удаления);
   - три-четыре ширины (360, 768, 1280, 1920);
   - обе темы;
   - состояния компонентов: обычный, наведение, фокус, нажатие, отключён, ошибка, загрузка.
4. **Дизайн-токены** в виде таблицы и в виде готовых CSS-переменных: цвета (с ролями, обе темы), типографика (семейства, размеры, межстрочные, насыщенность, `tabular-nums`), отступы, радиусы, тени/возвышение, границы, длительности и кривые анимации, ширины контейнеров, z-индексы.
5. **Спецификации компонентов**: список, строка траты, карточка траты (мобильная), панель фильтров, чип фильтра, выбор человека, выбор категории (чипы), поле суммы, поле даты, диалог/панель формы, диалог подтверждения, тост/баннер ошибки, скелетоны, пустые состояния, переключатель темы, кнопки (первичная, вторичная, опасная, текстовая, иконка), сводка/графики (если выбраны).
6. **Иконки и иллюстрации**: набор SVG для 7 категорий (+ запасная), для действий и пустых состояний; единый стиль, `currentColor`, сетка.
7. **Правила и принципы**: сетка и отступы, поведение при разных ширинах, максимальные длины текстов и как они обрезаются, что делать с очень длинным комментарием или огромной суммой.
8. **Передача разработчику**: структура компонентов в терминах React (какие блоки и пропсы), готовый CSS (переменные плюс классы) под существующую структуру, комментарии по анимациям. Если предлагается новая библиотека, объясни зачем, сколько весит и что без неё.
9. Короткая **записка с решениями**: что и почему выбрано, какие компромиссы, что оставлено на потом.

Если какой-то из пунктов ТЗ противоречит хорошему интерфейсу, не молчи: предложи лучшее решение и объясни, чем оно лучше.

## 13. Технические рамки реализации

- Фронтенд: **React 18 + TypeScript + Vite**, сейчас чистый CSS с переменными, без UI-библиотек. Тесты: Vitest для чистой логики.
- Допустимо добавить **небольшую** зависимость, если она реально экономит усилия (например, иконки или график), но с обоснованием и размером. Предпочтительно без.
- Интерфейс раздаётся статикой через nginx, к API ходит по `/api` (CORS не нужен).
- Уже есть и должно сохраниться: адресная строка как состояние фильтров, разбор суммы без `float` (строкой, до двух знаков), единый клиент API с типами, разбиение на `api / lib / hooks / components`.
- Валидация на клиенте повторяет правила сервера, но источник истины сервер: его ошибки показываются пользователю.

## 14. Чего делать не нужно

- Экраны входа, регистрации, профиля, настроек учётной записи.
- Уведомления (push, email), чат, поддержка.
- Мультивалютность, бюджеты, планирование, подписки, тарифы.
- Тяжёлые 3D, видео, звуки, фоновые анимации, отвлекающие от данных.
- Тёмные паттерны (навязчивые попапы, «геймификация» трат).

## 15. Критерии приёмки

Дизайн принимается, если:

1. Все четыре главных сценария (раздел 2) проходятся без лишних экранов и объяснений.
2. Проработаны **все** состояния из раздела 8 и все коды ошибок.
3. Обе темы выдерживают требования контраста (приложены значения).
4. Макеты читаются на 360 px и на 1920 px без горизонтального скролла.
5. Всё из раздела 12 передано в формате, который можно реализовать без догадок.
6. Решение работает на текущем API без доработок бэкенда (или такие доработки явно отделены и необязательны).
7. Первое впечатление «дорого и аккуратно»: единый язык компонентов, продуманные пустые состояния, микровзаимодействия, но без шума.
