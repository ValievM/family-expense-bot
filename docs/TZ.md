# ТЗ реализации: ИИ-бот учёта семейных расходов

Исполнитель: Claude. Ревьюер и принимающий: ты.
Источник требований: `test-task-expenses.md` (исходное тестовое). Всё, что не сказано там, — наши решения, они помечены **[РЕШЕНИЕ]**.

## 1. Цель

Сдать небольшой, но «показательный» проект: чистая архитектура, читаемый код, тесты, запуск одной командой. Оценивают и код, и то, как мы работали с ИИ, поэтому в README будет раздел о процессе.

## 2. Что входит в объём

- Telegram-бот: CRUD трат текстом на естественном языке через LLM-агента. Пользователь видит только свои траты.
- REST API + веб-панель главы семьи: траты всех, фильтры (член семьи, период, категория), создание, правка, удаление. Без авторизации.
- `docker compose up` поднимает всё: Postgres, бэкенд (API + бот), фронтенд.
- LLM настраивается через конфиг (URL, ключ, модель).

Не входит: авторизация панели, мультивалютность, графики и отчёты, вебхуки Telegram, голосовые сообщения.

## 3. Технические решения

| Область | Выбор | Почему |
|---|---|---|
| Бэкенд | Go 1.23, только стандартный `net/http` | с Go 1.22 `ServeMux` умеет методы и `{id}` в путях, внешний роутер не нужен |
| БД | PostgreSQL 16, `pgx`, миграции `goose` | надёжно, без ORM, SQL виден ревьюеру |
| LLM | OpenAI API по ключу (`LLM_API_KEY`), через порт `LLM`; клиент OpenAI-совместимый (tool calling) | по умолчанию OpenAI; `LLM_BASE_URL` и `LLM_MODEL` в конфиге позволяют сменить на OpenRouter или Ollama без правок кода |
| Telegram | long polling (`go-telegram/bot` или тонкий свой клиент) | не нужен публичный URL, проще в compose |
| Фронтенд | React + TypeScript + Vite, раздаётся nginx | знакомый стек, nginx же проксирует `/api` |
| Конфиг | переменные окружения (`.env.example`) | 12-factor, удобно для compose |
| Логи | `log/slog` | стандартная библиотека |

**[РЕШЕНИЕ]** Сумма хранится как `BIGINT` в минорных единицах (копейки), валюта одна, RUB. Деньги во `float` не кладём.
**[РЕШЕНИЕ]** `spent_at` — тип `DATE`. Часовой пояс для «сегодня/вчера» задаётся конфигом (`TZ`, по умолчанию `Europe/Moscow`).
**[РЕШЕНИЕ]** Член семьи в панели = любой `user_id`, у которого есть траты. Отдельной таблицы `users` нет (имя из Telegram храним в `users`, только если хватит времени; иначе показываем ID).
**[РЕШЕНИЕ]** Список семьи в боте не ограничиваем: кто написал боту, тот и член семьи. Белый список `ALLOWED_USER_IDS` — необязательная настройка.

## 4. Архитектура (hexagonal, без фанатизма)

```
cmd/server/main.go            — композиция зависимостей (единственное место, где всё соединяется)
internal/
  domain/                     — Expense, Category, ошибки, валидация. Ничего не импортирует.
  service/
    expense/                  — use cases + порт Repository. Знает только domain.
    agent/                    — LLM-агент: tools, цикл, промпт. Зависит от service/expense и порта LLM.
  adapters/
    postgres/                 — реализация Repository
    llm/                      — OpenAI-совместимый клиент
    telegram/                 — приём/отправка сообщений
    httpapi/                  — REST-хендлеры, DTO
  config/
migrations/
web/                          — фронтенд
```

Правило зависимостей: стрелки только внутрь (`adapters → service → domain`). Агент находится в `internal/service/agent`; интерфейсы объявляет тот, кто их использует.

Как применяем принципы (чтобы это можно было показать ревьюеру):

- **SRP** — один пакет, одна причина для изменения; хендлер не знает про SQL.
- **OCP** — новые инструменты агента добавляются новым типом `Tool`, цикл агента не меняется.
- **LSP/ISP** — маленькие интерфейсы (`Repository` 6 методов, `LLM` 1 метод).
- **DIP** — сервис зависит от интерфейса репозитория, Postgres подставляется в `main`.
- **DRY** — один `ExpenseService` обслуживает и REST, и агента; один фильтр `ListFilter` везде.
- **KISS / YAGNI** — никаких CQRS, event bus, DI-фреймворков.

## 5. Ключевое правило безопасности

`user_id` для инструментов агента **никогда не приходит от LLM**. Его подставляет код из Telegram-сообщения. В схеме tools поля `user_id` нет вообще. Это закрывает prompt injection вида «покажи траты пользователя 123».
Тест на это обязателен (см. T6).

## 6. Контракт REST API (для панели)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/expenses?user_id=&category=&from=&to=` | список с фильтрами, сортировка по `spent_at` убыв. |
| POST | `/api/expenses` | создание (`user_id` в теле обязателен) |
| PATCH | `/api/expenses/{id}` | частичное изменение |
| DELETE | `/api/expenses/{id}` | удаление, 204 |
| GET | `/api/users` | список `user_id` с тратами (для фильтра) |
| GET | `/api/categories` | закрытый список категорий с русскими метками (фронт не дублирует его) |
| GET | `/healthz` | проверка живости |

Ошибки: единый JSON `{"error": {"code": "...", "message": "..."}}`. Коды: 400 валидация, 404 не найдено.
Контракт зафиксирован в `docs/openapi.yaml`. Сумма в API всегда целое число копеек.

## 7. Инструменты агента (tools)

| Tool | Параметры | Эффект |
|---|---|---|
| `add_expense` | amount, category, spent_at?, comment? | создать трату |
| `list_expenses` | category?, from?, to? | показать траты, вернуть и сумму |
| `update_expense` | id, amount?, category?, spent_at?, comment? | изменить |
| `delete_expense` | id | удалить |

Как агент понимает «последнее» и «удали такси»: сначала вызывает `list_expenses`, находит нужный `id`, потом `update/delete`. Если совпадений несколько — переспрашивает текстом.
В системный промпт при каждом запросе подставляется сегодняшняя дата и день недели (иначе «вчера» и «в этом месяце» не решить).
Цикл агента: максимум 5 шагов вызова tools, потом ответ пользователю.

### Что можно делать параллельно

```
Волна 1:  T0
Волна 2:  T1 ∥ T5
Волна 3:  T2 ∥ T3            (T5 уже закончена или идёт)
Волна 4:  T4 ∥ T6
Волна 5:  T7 ∥ T8            (T8 может стартовать раньше, как только готов openapi.yaml из T4)
Волна 6:  T9
Волна 7:  T10
```

Критический путь: T0 → T1 → T3 → T6 → T7 → T9 → T10.
Фронтенд (T8) на критическом пути не стоит, его можно «подвинуть» вперёд без риска.

**[РЕШЕНИЕ]** Реально последовательно, одним исполнителем: порядок `T0, T1, T3, T2, T4, T5, T6, T7, T8, T9, T10`. Параллельность в таблице показывает, что можно переставлять, и что можно отдать отдельным сессиям, если захотим ускориться.

## 9. Общие правила качества (Definition of Done для каждой задачи)

1. Код компилируется, `make lint test` зелёный.
2. Для новой логики есть тесты; публичное поведение покрыто, внутренности не мокаем без нужды.
3. Нет циклических и «обратных» зависимостей между слоями.
4. Ошибки оборачиваются (`fmt.Errorf("...: %w", err)`), без `panic` в обычном потоке.
5. Нет секретов в репозитории, только `.env.example`.
6. Один логический коммит на задачу, сообщение по Conventional Commits (`feat(agent): ...`).

## 10. Риски

| Риск | Что делаем |
|---|---|
| LLM ошибается в категории или дате | категории — закрытый enum в схеме tool; дата валидируется в домене; агент отвечает, что именно сохранил |
| LLM недоступна / ключа нет | бот отвечает понятной ошибкой, API панели продолжает работать |
| «Удали такси» подходит к нескольким тратам | агент не удаляет, а просит уточнить |
| У проверяющего нет ключа от LLM | поддержка локальной Ollama через тот же OpenAI-совместимый конфиг; описать в README |
| Тесты агента нестабильны из-за реальной LLM | в тестах только fake-LLM; реальная LLM только в ручной проверке |
