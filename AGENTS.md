# AGENTS.md: правила работы над проектом

Проект: Telegram-бот и веб-панель учёта семейных расходов (Go, PostgreSQL, React, один `docker compose`).
Полное ТЗ: `docs/TZ.md`. **Это источник истины**: задачи, зависимости, архитектура, API, tools агента, решения. Прочитай его целиком перед началом. Если считаешь, что ТЗ нужно изменить, не меняй молча: опиши в отчёте как «Отклонение».

## Роли

- Ты (Codex) исполнитель: пишешь код, тесты, коммиты.
- Claude проводит ревью после каждой задачи и возвращает замечания.
- Владелец проекта (Магомед) читает отчёты и подтверждает переходы.

## Порядок работы

Берёшь **ровно одну задачу** из раздела 8 ТЗ за раз, в порядке: `T0, T1, T3, T2, T4, T5, T6, T7, T8, T9, T10` (T5b позже и только по отдельной команде).

1. Проверь, что все задачи из колонки «Блокируется» уже закрыты. Если нет, остановись и скажи.
2. Реализуй задачу строго в рамках её критерия готовности. Ничего «заодно».
3. Прогони проверки (`make lint test`, а для задач с БД и Docker ещё и соответствующие команды). Приведи реальный вывод, не пересказ.
4. Закоммить (см. ниже), `git push origin main`.
5. Выведи отчёт в формате ниже и **остановись**. Не начинай следующую задачу, пока не получишь «go». Если пришли замечания ревью, исправь их отдельным коммитом и снова выведи отчёт.

Работаем прямо в `main`, без feature-веток. Один коммит = одна логическая вещь (допускается несколько коммитов на задачу).

## Коммиты

Conventional Commits, английский, повелительное наклонение, строка до 72 символов:
`feat(domain): add Expense entity and validation`

Типы: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `build`, `ci`.
Область (scope) = пакет или слой: `domain`, `expense`, `agent`, `postgres`, `httpapi`, `telegram`, `llm`, `web`, `docker`, `config`.
Запрещено: `wip`, `update`, `fix stuff`, `.`, смешивание рефакторинга и фичи в одном коммите, коммиты с красными тестами, закоммиченные секреты и бинарники.
В теле коммита пиши «почему», если это не очевидно.

## Требования к коду

- Архитектура, слои и правило зависимостей из раздела 4 ТЗ. `domain` ничего не импортирует. Интерфейсы объявляет потребитель.
- Принципы: SOLID, DRY, KISS, YAGNI. Без DI-фреймворков, CQRS, event bus, лишних абстракций «на вырост».
- Только стандартный `net/http` (Go 1.22+ `ServeMux`), `pgx`, `goose`, `log/slog`. Любую другую зависимость сначала обоснуй в отчёте.
- Ошибки: `fmt.Errorf("...: %w", err)`, доменные ошибки через `errors.Is/As`. Без `panic` в обычном потоке.
- Деньги: `int64` в копейках, никаких `float`.
- Тесты: table-driven, понятные имена, fake вместо моков там, где это возможно. LLM в тестах только fake.
- Комментарии должны нести информацию и не шуметь.
  - **У интерфейсов комментариев нет** (ни у типа, ни у методов): имена говорят сами, поведение описано у реализаций.
  - **Функции и методы с реальным поведением** получают ровно три строки на русском, без вводной и пустых строк:
    ```go
    // Принимает: <параметры и их смысл; «ничего», если их нет>.
    // Делает: <что делает, включая побочные эффекты и правила>.
    // Возвращает: <что и когда возвращает, включая ошибки>.
    ```
  - **Без комментария**: тривиальные геттеры, обёртки `Error()`/`String()`, однострочные делегаты, тестовые фейки, стабы и хелперы, оболочка `main`, проверки `var _ Iface = ...`. У `Test…` одна строка `// Проверяет: ...`.
  - Строки до ~100 символов, без пересказа сигнатуры. Внутри функций только «почему», не «что».
  - Типы, константы и переменные: одна строка и только если назначение неочевидно. Пакет: `// Package name — описание`.
- Имена идентификаторов, код, коммиты: английский. Комментарии, отчёты и общение: русский.
- `gofmt`, `go vet` и `golangci-lint` обязаны быть чистыми.

## Безопасность

- `user_id` для tools агента **никогда не берётся из ответа LLM**, только из Telegram-сообщения (раздел 5 ТЗ). Нужен тест.
- Репозиторий публичный. Никаких ключей, токенов, `.env`, дампов. Только `.env.example` с пустыми значениями. `.env` в `.gitignore` с самой первой задачи.
- Никогда не проси и не печатай в чат реальные ключи и токены. До задачи T7 ключи не нужны.
- Не выполняй деструктивные команды (`rm -rf` вне проекта, `git push --force`, `git reset --hard` по опубликованной истории, `docker system prune`) без явной команды.

## Формат отчёта

После каждой задачи выведи ровно такой блок и остановись:

```
## REPORT T<N>: <название задачи>

**Статус:** done | blocked | partial
**Коммиты:**
- <короткий hash> <сообщение>

**Что сделано:** 2–5 пунктов по сути, не пересказ диффа.

**Файлы:** ключевые добавленные/изменённые файлы с одной строкой смысла.

**Проверка:**
<команда>
<реальный вывод, обрезанный до значимого>

**Критерий готовности из ТЗ:** выполнен | не выполнен (почему)

**Отклонения от ТЗ и решения:** что сделано иначе и зачем (или «нет»).

**Не проверено / риски:** честно, что не запускалось и что может сломаться (или «нет»).

**Вопросы:** только то, без чего нельзя двигаться дальше (или «нет»).

**Следующая задача:** T<M> (блокеры сняты: да/нет)
```

Правила отчёта: ничего не придумывай. Если тест не запускался, так и пиши. Если команда упала, приводи вывод ошибки. Не заявляй «всё работает» без запущенной проверки.

## Остановки

Остановись и спроси, не угадывай, если:
- ТЗ противоречит само себе или не покрывает ситуацию;
- нужен секрет, токен или доступ;
- задача блокируется незакрытой;
- требуется добавить зависимость, не названную в ТЗ.
